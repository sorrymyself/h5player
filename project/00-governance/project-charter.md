# Web Extension 重构项目章程

> 文档 ID：GOV-001  
> 状态：Approved  
> 负责人：项目维护者  
> 最后更新：2026-08-10  
> 评审周期：每个里程碑结束时

## 1. 背景

H5Player 油猴脚本已经长期运行并形成较稳定的功能集合，但其工程基础主要围绕单文件脚本发布建立：缺少完整单元测试与端侧测试、JavaScript 数据结构缺乏系统类型约束，运行时又高度依赖页面全局对象、GM API、DOM Hook 和站点特例。

当前 Web Extension 仅把 `web-extension/inject.main.js` 与 `src/h5player/index.js` 打包成 `inject.js`，再通过 content script 注入页面，并在 `inject.base.js` 中模拟部分 GM API。该方案可快速复用旧能力，却没有形成独立扩展的架构、权限模型、数据契约和质量体系。

由于 Web Extension 尚无正式用户，本项目以它作为低迁移风险的重构载体；油猴脚本继续稳定维护，待扩展架构经真实使用验证后，再单独评估是否反向抽取共享核心。

## 2. 愿景

建设一个可独立开发、测试、发布和演进的跨浏览器 Web Extension，使 H5Player 的通用媒体增强能力具备：

- 明确的产品范围与可追踪需求；
- 可替换、可测试的模块边界；
- TypeScript 与运行时 Schema 双重契约；
- 浏览器端真实加载的自动化验证；
- 最小权限、安全隔离和隐私透明；
- 可灰度、可诊断、可回滚的发布体系；
- 可持续维护的站点适配器机制。

## 3. 项目目标

### 3.1 业务目标

- 在 Chromium 与 Firefox 上提供一致的核心媒体控制体验。
- 覆盖通用 HTML5 视频页面、SPA、iframe、Shadow DOM 和多媒体实例等主要页面形态。
- 让设置、快捷键、站点开关和诊断能力通过扩展原生 UI 可管理。
- 先建立可靠的核心能力，再逐步迁移高风险实验功能。

### 3.2 工程目标

- 新扩展业务代码 100% 使用 TypeScript 严格模式。
- 所有跨上下文消息、持久化数据和导入数据经过运行时校验。
- 领域逻辑不直接依赖 `chrome.*`、`browser.*`、Vue 或具体页面全局变量。
- PR、夜间构建和发布候选分别具备自动化质量门禁。
- 关键能力可在固定测试页面中与 Legacy 行为做差分验证。

### 3.3 治理目标

- 每项开发工作都可追溯到需求 ID、任务 ID 和验收证据。
- 架构、权限、数据格式和公共 API 的重大变化必须记录 ADR。
- 里程碑结束必须更新进度、风险与基线审查记录。

## 4. 明确边界

### 4.1 本项目包含

- 重建 `web-extension/` 的工程结构、构建体系和运行架构。
- 设计通用媒体核心、命令系统、站点适配、配置存储、UI 和浏览器能力适配层。
- 建立自动化测试、CI、发布、诊断、安全和维护体系。
- 以 Legacy 功能作为行为参考，分阶段实现扩展功能。
- 提供显式的配置导入/导出与未来 Legacy 数据迁移格式。

### 4.2 本项目不包含

- 对 `src/h5player/`、`src/libs/` 或油猴构建链进行全量 TypeScript 迁移。
- 为了代码复用而直接修改稳定油猴逻辑。
- 在第一版中保证所有历史站点特例、实验下载或网络 Hook 完全等价。
- 在未经决策和隐私审查时加入远程遥测、远程代码或远程开关。
- 初期支持 Safari、移动浏览器或 Manifest V2。

## 5. Legacy 保护规则

1. 默认只读范围：`src/h5player/`、`src/libs/`、`config/rollup*`、`dist/h5player.user.js` 的既有发布行为。
2. 扩展重构 PR 不得顺带整理、重命名或格式化上述文件。
3. 若重构发现 Legacy 缺陷，单独登记 `LEGACY-*` 问题；只有影响现有用户的严重缺陷才进入独立修复流程。
4. Legacy 可以作为测试 Oracle 或行为资料，但不能成为新扩展运行时依赖。
5. 任何共享核心抽取必须在扩展稳定发布后，以新 ADR 和独立项目重新批准。

## 6. 指导原则

1. **稳定优先**：隔离新旧演进，避免重构风险回流到现有用户。
2. **能力边界优先**：先定义接口和信任边界，再实现功能。
3. **纵向切片优先**：每阶段交付可运行、可测试、可演示的用户能力。
4. **默认最小权限**：权限、消息和远程访问都按必要性逐项证明。
5. **自动化证据优先**：功能完成必须由测试、构建产物和审查记录证明。
6. **通用核心优先**：站点适配只处理例外，不反向污染核心。
7. **可撤销优先**：数据迁移、实验功能和发布都必须保留回退路径。

## 7. 成功标准

项目达到首个稳定版时至少满足：

- 核心功能需求 `FR-CORE-*` 全部完成，P0/P1 验收用例全绿。
- Chromium 最新两个稳定大版本和 Firefox 最新版/ESR 的发布矩阵通过。
- 不包含 CSP 改写、`unsafe-eval`、`new Function`、远程代码执行或未解释的高危权限。
- 类型检查、Lint、单元、组件、集成、扩展 E2E、打包和商店静态检查均进入 CI。
- 关键领域模块达到规定覆盖率；所有关键用户路径有真实扩展 E2E。
- 设置数据具备 Schema 版本、迁移测试、导出和恢复能力。
- 发布产物可复现，Chrome/Firefox 包、源映射策略、哈希和 SBOM 可追踪。
- 至少完成一轮 Beta 反馈与兼容性缺陷收敛，且无未处理 P0/P1 缺陷。

## 8. 角色与责任

角色可以由同一维护者兼任，但审查视角不可省略。

| 角色              | 主要责任                               |
| ----------------- | -------------------------------------- |
| Product Owner     | 需求优先级、范围取舍、发布目标         |
| Architect         | 上下文边界、模块接口、ADR 和技术债控制 |
| Feature Owner     | 纵向切片实现、测试和文档               |
| Quality Owner     | 测试策略、质量门禁、兼容矩阵           |
| Security Reviewer | 权限、消息、存储、隐私与供应链审查     |
| Release Manager   | 版本、构建、签名、灰度和回滚           |

重大里程碑的架构、安全和发布审查应尽量由非实现视角完成；若只能单人维护，至少分时进行并使用审查模板保存证据。

## 9. 关键假设与约束

- 扩展暂无已发布用户，因此允许重建其内部结构和数据模型。
- 油猴脚本行为并非天然正确；差分测试发现冲突时，由需求和安全原则决定是否保持兼容。
- 浏览器商店政策、Manifest V3 能力和权限提示是产品约束，不只是实现细节。
- 第三方站点随时变化，站点兼容性必须通过适配器、监控和分级支持管理，不能承诺永久全量兼容。
