# 项目文档管理规范

> 文档 ID：GOV-002  
> 状态：Approved  
> 最后更新：2026-08-10

## 1. 适用范围

所有与 Web Extension 重构有关的需求、任务、进度、风险、架构、审查、测试和发布资料均放入根目录 `project/`。面向最终用户的安装、功能和 FAQ 仍放入 `docs/`。

## 2. 目录规则

| 目录               | 内容                          | 禁止内容           |
| ------------------ | ----------------------------- | ------------------ |
| `00-governance/`   | 章程、术语、流程与文档规范    | 具体功能实现笔记   |
| `01-requirements/` | PRD、用户故事、验收、功能矩阵 | 代码设计细节       |
| `02-architecture/` | 架构、接口、数据模型、ADR     | 日常进度           |
| `03-roadmap/`      | 阶段、里程碑、依赖            | 细粒度任务日志     |
| `04-tasks/`        | Backlog、当前进度、任务流程   | 长期架构决策       |
| `05-quality/`      | 测试策略、门禁、兼容矩阵      | 未批准的功能需求   |
| `06-security/`     | 威胁模型、权限、隐私、供应链  | 密钥和真实隐私数据 |
| `07-release/`      | 版本、渠道、发布与回滚        | 商店账号凭证       |
| `08-operations/`   | 日志、诊断、支持与缺陷管理    | 用户原始敏感数据   |
| `09-reviews/`      | 基线审查、阶段评审、审查结论  | 无结论的临时草稿   |
| `templates/`       | 可复制模板                    | 具体项目实例       |

## 3. 文档头信息

正式文档顶部至少包含：

```text
文档 ID：领域缩写-序号
状态：Draft | In Review | Approved | Superseded | Archived
负责人：姓名或角色
最后更新：YYYY-MM-DD
关联需求/任务/ADR：可选
评审周期：可选
```

## 4. 命名与编号

- 普通文档使用小写 kebab-case，例如 `test-strategy.md`。
- 日期型审查记录使用 `主题-YYYY-MM-DD.md`。
- ADR 使用 `ADR-0001-short-title.md`，编号永久不复用。
- 需求 ID：`FR-*`（功能）、`NFR-*`（非功能）、`SEC-*`（安全）。
- Epic ID：`EPIC-00`；任务 ID：`EXT-000`；缺陷 ID：`BUG-000`；Legacy 问题：`LEGACY-000`。
- 风险 ID：`RISK-000`；决策待办：`DECISION-000`。

## 5. 状态流转

### 5.1 文档

`Draft -> In Review -> Approved -> Superseded/Archived`

- Draft：允许快速修改，不能作为发布依据。
- In Review：范围已稳定，正在审查。
- Approved：当前有效事实源。
- Superseded：被新文档或 ADR 取代，必须链接替代项。
- Archived：历史资料，不再适用。

### 5.2 任务

`Proposed -> Ready -> In Progress -> In Review -> Verified -> Done`

可使用 `Blocked` 标记阻塞，但必须记录阻塞原因、责任方和下一次检查时间。

## 6. 变更规则

- 修改 Approved 需求时，必须同步检查功能矩阵、路线图、任务和测试。
- 修改公共接口、权限、持久化 Schema、上下文边界或浏览器支持范围时，必须新增或更新 ADR。
- 删除需求或任务不得直接抹除历史；标记 `Cancelled` 并写明原因。
- 里程碑结束后，将阶段审查结果写入 `09-reviews/`，进度页只保留最新摘要。
- 任何文档中的“以后优化”“尽量”“兼容大部分”等模糊词，都必须补充可验证指标或登记待决问题。

## 7. 追踪关系

每个实现任务至少关联一个需求；每个 P0/P1 需求至少关联：

- 一个任务或 Epic；
- 一个或多个自动化测试层级；
- 一个验收标准；
- 若涉及重大设计，一个 ADR。

建议在 PR 描述中使用：

```text
Requirement: FR-CORE-001
Task: EXT-120
ADR: ADR-0003
Verification: unit / integration / e2e
```

## 8. 评审节奏

- 每个 PR：任务与关联文档检查。
- 每周或每个开发周期：更新 `04-tasks/progress.md`。
- 每个里程碑：需求、架构、质量、风险和发布准备评审。
- 每个正式版本：发布复盘和兼容矩阵更新。
- 每季度：清理过期决策、风险与站点支持等级。

## 9. 文档完成标准

一份正式文档只有同时满足以下条件才能标记 Approved：

- 目标读者和适用范围明确；
- 决策与待决问题区分清楚；
- 关键陈述有代码、测试、Issue 或 ADR 证据；
- 验收项可测试；
- 与同领域事实源没有冲突；
- 所有相对链接有效；
- 包含负责人和更新时间。
